# Subscription Activation Implementation Plan

## Status

Implementation design for the Initial Subscription Activation increment, approved architecture per [ADR-011](./decisions/ADR-011-Initial-Subscription-Activation.md) and [docs/34](./34_SUBSCRIPTION_ACTIVATION_ARCHITECTURE.md), with exact column-level detail in [docs/35](./35_SUBSCRIPTION_ACTIVATION_ERD.md). This document does not reopen, reinterpret, or contradict any locked ADR-011 decision. No PHP code, migration, or test is created by this document.

**CTO decisions locked 2026-07-22** (superseding every "recommendation, pending CTO approval" framing this document previously used): (1) `TenantId` is reserved at `ClinicRegistration::submit()` — no `Approved`/`UnderReview` status is introduced, and the identifier is generated by an Application-layer generator, never by the aggregate. (2) `UNIQUE(subscriptions.tenant_id)` and `UNIQUE(subscriptions.payment_id)` are approved; `UNIQUE(commercial_offer_id)` is not added. (3) Supersession is serialized by a fixed lock order (Payment, then `clinic_registrations`) and resolved by transaction-commit order, never by timestamp. (4) No migration backfills a historical `TenantId`; a preflight-query gate decides whether tightening may proceed. (5) `TenantId` crosses module boundaries only as an opaque UUID string — no Shared Kernel, no cross-domain Domain-VO import. (6) The Payment-side integration event gains `event_version = 1` before this consumer is wired. (7) The Subscription outbox is Option A. Every section below reflects these as settled, not proposed.

## TenantId Propagation Design

**Locked CTO Decision 1**: `TenantId` is reserved at `ClinicRegistration::submit()` (`Draft → Submitted`) — the smallest possible change to an already-existing, already-tested method, and no `Approved`/`UnderReview` status is introduced. Generation is strictly an Application-layer responsibility: the aggregate must not depend on an identifier-generator interface, must never generate the identifier itself, must receive it as a parameter to `submit()`, must reject any attempt to replace an already-reserved value, and must preserve it unchanged through reconstitution. Conceptually: `tenantId = application generator generates once; clinicRegistration.submit(tenantId, occurredAt); repository persists the immutable identifier`.

| Aggregate | Constructor/factory argument | Readonly/mutable | Reconstitution argument | Accessor | Persistence column | Mapper change | Invariant validation |
|---|---|---|---|---|---|---|---|
| `ClinicRegistration` | New: `?TenantId $reservedTenantId` added to the constructor (nullable to preserve `Draft`-state construction via `start()`, where no reservation exists yet) | Set once, inside `submit(TenantId $tenantId, DateTimeImmutable $occurredAt)`, via a new private setter path — never reassigned afterward | New: the reconstitution factory (if one is later added; today `PostgresClinicRegistrationRepository` hydrates directly — see below) must accept the persisted value unchanged | New: `public function reservedTenantId(): ?TenantId` | New: `clinic_registrations.reserved_tenant_id` (per [docs/35](./35_SUBSCRIPTION_ACTIVATION_ERD.md#clinic_registrations-existing-table-one-new-column)) | `ClinicRegistrationRepositoryInterface`'s Postgres implementation must read/write the new column | `submit(TenantId $tenantId, DateTimeImmutable $occurredAt)` must reject being called twice (already enforced — `assertMutableDraft`/status guard prevents re-submission) and must reject a call that would replace an already-set `reservedTenantId` (defense-in-depth, independent of the status guard). `submit()` **receives** the already-generated `TenantId` as a parameter — it never generates one itself and depends on no generator interface. Generation happens one call earlier, in `SubmitClinicRegistrationService` (Application layer), via a new `ClinicRegistrationTenantIdGeneratorInterface` (single method `generate(): string`, mirroring the existing `ClinicRegistrationIdentifierGeneratorInterface` pattern) — that interface is bound and called only in the Application layer, never imported by `ClinicRegistration` itself. |
| `CommercialOffer` | `prepare()` gains a new required `TenantId $tenantId` argument, supplied by the caller from the ClinicRegistration it already loads | Readonly, set once at `prepare()` | N/A (no reconstitution factory shape change beyond passing the persisted value through) | New: `public readonly TenantId $tenantId` (or equivalent property) | New: `commercial_offers.tenant_id` | `PostgresCommercialOfferRepository`'s row-mapping method | `prepare()` must reject a null/invalid `TenantId` (existing UUID-validation VO pattern) |
| `Payment` | `Payment::create()` gains a new required `PaymentReference $tenantId`-shaped argument (or a dedicated `TenantId`-equivalent VO, matching Payment's own existing `PaymentReference` convention for cross-aggregate identifiers), supplied by `CreatePaymentService` from the claimed CommercialOffer | Readonly, set once at `create()` | Existing `PaymentPersistenceMapper`'s `toDomain()` must accept the new column | New accessor via the existing public-property convention (`Payment` already exposes fields as public readonly-by-convention properties) | New: `payments.tenant_id` | `PaymentPersistenceMapper` | `CreatePaymentService` must reject a CommercialOffer with no `tenant_id` (should be structurally impossible once the CommercialOffer-side change lands, but the Application-layer check remains defense-in-depth per the project's own stated posture) |

**Unit tests** (to be written when this plan is implemented, not now): `ClinicRegistrationTest`'s `submit()` coverage gains an assertion that `reservedTenantId()` becomes non-null exactly once, and that calling `submit()` a second time is still rejected by the existing guard (proving the reservation-generation path doesn't accidentally weaken that invariant). `CommercialOfferTest`/`PaymentAggregateTest` gain construction-time assertions that a missing/invalid `TenantId` argument is rejected.

**PostgreSQL tests**: a new focused test proving `clinic_registrations.reserved_tenant_id` is set after `submit()` and is `UNIQUE`; the existing `PostgresCommercialOfferRepositoryTest`/`PostgresPaymentRepositoryTest` gain assertions that `tenant_id` round-trips correctly through save/reload.

**Non-negotiable invariants, all satisfied by this design**: generated exactly once (only `SubmitClinicRegistrationService`'s call to the Application-layer generator, guarded by the existing single-submission invariant on the aggregate side); the Domain aggregate never generates it and depends on no generator interface; non-null (once past `Submitted`, every downstream aggregate's constructor requires it, per the table above); immutable (no setter exists past the single assignment point in each aggregate, and `submit()` rejects any attempt to replace an already-reserved value); never inferred from another row (each aggregate receives it as an explicit argument from its own caller, never queried back from a different table); never backfilled during Subscription activation (the activation transaction only ever *reads* `payments.tenant_id`, which was already fixed at Payment-claim time — it never writes or infers a tenant_id itself).

## Source Event Registration

**`source_event_id`** = `payment_integration_outbox.id` of the specific `VerifiedPaymentSucceeded` row (the outbox's own stable PK, already a random UUID per this session's own prior fix).

**`payment_id` extraction**: from `PaymentIntegrationOutboxEvent::$paymentId` (already a typed constructor property on the event the consumer receives — no parsing of the JSON payload required for this field specifically, since the event DTO already carries it structurally).

**Event type validation**: the queue listener subscribes only to `PaymentIntegrationOutboxEvent` instances where `$event->type === 'VerifiedPaymentSucceeded'` — any other `type` value on the same event class (e.g. a future, different Payment-side event reusing the same outbox table) is ignored by this listener, not registered, not erred.

**Event version validation — locked CTO Decision 6, a mandatory precondition, not a soft note.** `payment_integration_outbox` has no `event_version` column today. Before this consumer is wired, `payment_integration_outbox`/`PaymentIntegrationOutboxEvent` must gain `event_version`, starting at `1` — an additive, non-behavior-changing hardening change to the existing Payment-side integration event contract (no Payment Domain state behavior changes). This is a prerequisite step for this plan's own Implementation Increment Plan, not an out-of-scope observation.

**Consumer policy for the source event, exactly as locked**:

| Condition | Outcome |
|---|---|
| `$event->type` is not `VerifiedPaymentSucceeded` | Ignored — no application registered, no log, no error (normal, expected traffic for other event types sharing the dispatcher). |
| `$event->type === 'VerifiedPaymentSucceeded'` and `event_version === 1` | Registered — proceeds through the normal registration/claim/transaction sequence. |
| `$event->type === 'VerifiedPaymentSucceeded'` and `event_version` is present but not `1` | Quarantined — a recognized event type at a version this consumer does not yet support. |
| Malformed normalized identifiers (empty/invalid `payment_id`, or any required field missing) | Quarantined. |
| Duplicate `source_event_id` | Returns or reuses the existing activation application (the existing idempotent `register()` insert already produces this behavior). |

This table supersedes this document's earlier framing of `event_version` as "noted for awareness, not blocking" — it is now a required precondition, and [Migration Order](#migration-order)/[Implementation Increment Plan](#implementation-increment-plan) below reflect it as a discrete step.

**Duplicate registration**: `register()` is `INSERT ... ON CONFLICT (source_event_id) DO NOTHING`-equivalent, then re-select by `source_event_id` — identical idiom to `PostgresPaymentVerificationApplicationRepository::register()`, already proven this session.

**Queue job payload**: the listener registers the application synchronously (a fast, single-row idempotent insert) and dispatches `ActivateSubscriptionJob($applicationId)` — **the job constructor receives only the opaque `subscription_activation_applications.id` string**, never the raw event, never the Payment ID directly, never the payload. No provider call happens anywhere in this path.

## Supersession and Double-Activation Strategy

**Locked CTO Decision 3 — the deterministic, database-enforceable meaning of "newer valid activation"**: never wall-clock creation time. It is **whichever activation transaction is the first to successfully commit**, under a fixed lock order: (1) lock Payment, (2) lock `clinic_registrations` (the tenant's stable, already-existing parent row), (3) query `subscriptions` by `tenant_id`, (4) the first valid transaction to commit wins. Any other Payment for the same tenant, revalidated *after* acquiring that same lock, deterministically observes the first one's already-committed result and completes with status `ignored`, result code `superseded` — this requires no timestamp comparison at all, never uses CommercialOffer as the concurrency parent, and never introduces a new purchase identity.

**Why not CommercialOffer or a new business identity**: `commercial_offers.clinic_registration_id` is not unique — one Clinic Registration may legitimately produce more than one CommercialOffer over time (an expired offer followed by a fresh checkout). CommercialOffer is therefore not the correct "one initial Subscription per X" identity; `clinic_registrations` (equivalently, its `reserved_tenant_id`) is the correct, already-existing, already-stable parent, and no new business identity needs to be invented.

**Guard comparison**:

| Guard | Prevents | Verdict |
|---|---|---|
| `UNIQUE(payment_id)` on `subscriptions` | The *same* Payment activating twice | Necessary, already locked by ADR-011, **not sufficient alone** |
| `UNIQUE(commercial_offer_id)` on `subscriptions` | The same CommercialOffer activating twice | Redundant given `payments.commercial_offer_id` is already unique (one Payment per CommercialOffer) — adds no protection `UNIQUE(payment_id)` doesn't already give |
| `UNIQUE(clinic_registration_id)` for "active initial subscriptions" (partial index) | Two Subscriptions for the same registration | Workable, but `UNIQUE(tenant_id)` (see below) is simpler and does not require a partial-index predicate, since this increment never creates more than one Subscription row per tenant under any circumstance |
| Advisory locks | The concurrent-insert race | Works, but is a session-scoped, less discoverable mechanism than a row lock on a real table already participating in the transaction; adds an operational concept (advisory lock key management) with no corresponding benefit here |
| A new application-owned "purchase identity" | The race, in principle | **Rejected — explicitly prohibited by locked CTO Decision 3** — would be inventing a new business identity beyond what ADR-011 already approved (TenantId, Payment, CommercialOffer); not justified when the existing identity chain already suffices |
| **Row-locking `clinic_registrations` (by the resolved `tenant_id`'s owning registration) + `UNIQUE(tenant_id)` on `subscriptions`** | **All four races listed in this section** | **Approved and locked (CTO Decisions 2 and 3)** |

**Proof for each required race**:
- *Same Payment creating two Subscriptions*: blocked by `UNIQUE(payment_id)` on `subscriptions` (ADR-011, already locked) and by `UNIQUE(payment_id)` on `subscription_activation_applications` (also already locked) — a duplicate delivery for the same Payment never even reaches a second attempt to create a row.
- *Same source event creating two applications*: blocked by `UNIQUE(source_event_id)` on `subscription_activation_applications` (already locked).
- *Two different successful Payments creating two initial Subscriptions for the same tenant*: blocked by the row lock on `clinic_registrations` serializing both transactions' eligibility-recheck-and-insert sequence, backstopped by `UNIQUE(tenant_id)` on `subscriptions` (**locked, CTO Decision 2**) in case the lock is ever bypassed or misapplied.
- *Two concurrent workers creating two Subscription rows when neither exists yet*: same mechanism — the second worker's transaction blocks on the row lock until the first commits or rolls back, then re-checks "does a Subscription already exist for this tenant" and finds the answer deterministically.

**This mechanism is approved and locked** — see the [ERD Approval Checklist](#erd-approval-checklist), now satisfied.

## Subscription Persistence Design

`SubscriptionRepositoryInterface` (new, Contracts):

```php
interface SubscriptionRepositoryInterface
{
    public function find(SubscriptionId $id): ?Subscription;
    public function findByTenantId(TenantId $tenantId): ?Subscription;
    public function findByPaymentId(string $paymentId): ?Subscription;
    public function save(Subscription $subscription): void;
}
```

- `find`/`findByTenantId`/`findByPaymentId` each map directly to the ERD's PK/`UNIQUE(tenant_id)`/`UNIQUE(payment_id)` — no query needs a tenant *filter parameter* separately, since `tenant_id` is either the lookup key itself or already implicit in the row found. (`find(SubscriptionId, TenantId)` as literally suggested by the task's own prompt is redundant once `UNIQUE(tenant_id)` exists — a caller who has both would use `findByTenantId` and can compare the returned `id` if it needs to; adding a second-parameter overload would just be two ways to ask the same question. Flagged here as a deliberate simplification, not an oversight.)
- `save()` for this increment is **always an insert** (Subscription does not exist before this transaction) — no optimistic-locked update path is exercised. The interface still accepts a full aggregate (not an "insert-only" narrower type) so that a future renewal/reactivation increment can extend the same repository with an update path without changing this method's signature.
- **Duplicate-key translation**: an insert that violates `UNIQUE(payment_id)` or `UNIQUE(tenant_id)` must be caught and translated into the same `TransientPaymentApplicationException`-equivalent (a new `TransientSubscriptionActivationException`) the retry-classification layer already expects — **but only for the `UNIQUE(payment_id)` case**, since that violation is genuinely transient/retry-worthy (extremely unlikely given the application-level `UNIQUE(payment_id)` on the applications table already prevents duplicate processing of the same Payment) — a `UNIQUE(tenant_id)` violation, by contrast, is not a transient failure to retry; it is the **expected, correct signal** that another Payment already won this tenant's activation, and must be translated into the `superseded`/`ignored` outcome path directly, not a retry.
- **Stale-version translation**: not exercised by this increment (no update path is used), but the interface's future extension point should reuse the exact `StalePaymentWriteException`-equivalent pattern already proven for `PostgresPaymentRepository`.
- **Hydration/reconstitution**: a new `PostgresSubscriptionRepository` (Infrastructure) constructs `Subscription` via its existing, unmodified `reconstitute()` factory — no change to that method's signature.
- **Domain event handling**: `Subscription::releaseEvents()` already exists; this increment's activation service calls it and passes the result to a `SubscriptionEventPublisherInterface`-equivalent (mirroring `ClinicRegistrationEventPublisherInterface`'s existing shape) for **in-process domain events only** — this is distinct from, and must not be confused with, the `subscription_integration_outbox` mechanism, which is the cross-module integration channel. Domain events (`SubscriptionCreated`, `SubscriptionActivated`, etc.) remain in-process signals within the Subscription & Billing module; only the one approved `SubscriptionActivated` **integration** event crosses the outbox boundary.

**Added references on Subscription, per the ERD**: `clinic_registration_id`, `payment_id`, `commercial_offer_id`.

| Reference | Business invariant | Why it belongs on Subscription | Immutable? | Initial-activation lineage only? | Must a future renewal Payment overwrite it? |
|---|---|---|---|---|---|
| `payment_id` | One Payment activates at most one Subscription | It is the activation identity itself (`UNIQUE`), not merely a convenience join | Yes | Yes — this is specifically the *initial-activation* Payment | **No** — a future renewal increment must not overwrite this column; it needs its own, separate representation for "which Payment most recently renewed this Subscription," out of this document's scope to design |
| `clinic_registration_id` | Traceability from Subscription back to its originating registration | Operational/support traceability — never a live join, never used for a business decision at read time | Yes | Yes | No — never overwritten, regardless of future renewal design |
| `commercial_offer_id` | Traceability from Subscription back to the checkout snapshot that produced it | Same traceability justification as above | Yes | Yes | No — never overwritten |

None of these three references is added "merely for query convenience" — each is justified above by a specific invariant or traceability need already implied by ADR-011's own transaction sequence (the activation service must load Payment and CommercialOffer by these exact identifiers).

## Activation Application Design

Data model: exactly the columns in [docs/35](./35_SUBSCRIPTION_ACTIVATION_ERD.md#subscription_activation_applications).

**Status transitions** (identical shape to `PaymentVerificationApplicationStatus`, renamed per ADR-011):

```text
pending ──claim──> processing ──complete(applied)──────────> applied [terminal]
                              ──complete(ignored)──────────> ignored [terminal]
                              ──complete(reconciliation_required)─> reconciliation_required [terminal]
                              ──complete(quarantined)──────> quarantined [terminal]
                              ──complete(retry_pending)────> retry_pending ──claim (after next_attempt_at)──> processing (loop)
                              ──complete(exhausted, after max attempts)──> exhausted [terminal]
retry_pending ──claim (lease-eligible)──> processing (loop, above)
processing (lease expired, never completed) ──claim (new token)──> processing (reclaimed)
```

`already_reflected` is a **result code**, never a status — it is always paired with status `applied` (an idempotent no-op is still, from the application-record's own point of view, a successfully-terminal "applied" outcome; the *distinction* between "genuinely created a Subscription" and "recognized an already-applied duplicate" lives entirely in `result_code`, not `status`). This matches the CTO's own explicit instruction and mirrors how `PaymentVerificationApplicationResultCode::AlreadyReflected` pairs with status `applied`/`processed` today.

**Register**: idempotent insert on `source_event_id`, generates `subscription_id` fresh only on first insert (an `ON CONFLICT DO NOTHING` naturally leaves the losing candidate's generated UUID unused, exactly as this session's outbox work already proved for the analogous case).

**Claim**: atomic conditional `UPDATE ... WHERE status='pending' OR (status='retry_pending' AND next_attempt_at<=now) OR (status='processing' AND processing_lease_expires_at<=now) RETURNING *`, identical to `PostgresPaymentVerificationApplicationRepository::claim()`.

**Retry scheduling**: `SubscriptionActivationRetryPolicy` (new, independent class — lease 2 min, max 5 attempts, base delay 5s, max delay 2 min, ±20% jitter), used only for transient failures (Postgres serialization/lock-timeout, unexpected constraint races that are genuinely retry-worthy — see [Subscription Persistence Design](#subscription-persistence-design)'s duplicate-key-translation note).

**Stale-token behavior**: `complete()` conditional on `id`, exact `claim_token`, `status='processing'` — a stale token affects zero rows, identical to the proven pattern.

**Completion behavior**: same shape as `PostgresPaymentVerificationApplicationRepository::complete()`, extended with the extra terminal statuses this increment's outcome policy requires (`ignored`, `reconciliation_required`, `quarantined` as first-class statuses, not just result codes, per the CTO's own locked lifecycle list).

**Terminal-state / exhausted / reclaim behavior**: identical in shape to the proven Payment-side pattern — `exhausted` only after `attempt_count >= maxAttempts` on a transient-failure path; all four other terminals never retry.

## Activation Transaction Sequence

Reproduced here at implementation precision (docs/34 already states the high-level sequence; this section fixes the exact read/write order and lock points):

**A. Event registration** (outside any financial transaction; a single fast idempotent insert):
1. Queue listener receives `PaymentIntegrationOutboxEvent`, filters on `type === 'VerifiedPaymentSucceeded'`.
2. `SubscriptionActivationApplicationRepositoryInterface::register($sourceEventId, $paymentId, $tenantId, $now)` — idempotent insert, resolves `tenant_id` by reading the Payment row's own `tenant_id` column at this point (a plain, unlocked read — safe, since this is only for audit/traceability on the application row, not a decision).
3. Dispatch `ActivateSubscriptionJob($applicationId)` `afterCommit()`.

**B. Application claiming** (a single atomic statement, not itself inside the financial transaction):
4. `ActivateSubscriptionJob::handle()` calls `ActivateSubscriptionFromVerifiedPaymentService::execute($applicationId)`.
5. The service calls `claim($applicationId, $now, $leaseSeconds)`. If null, return (already claimed elsewhere, or terminal).

**C. Transactional application** (one PostgreSQL transaction, opened only after a successful claim):
6. Reload the claimed application by `id` (defensive — the claim `UPDATE ... RETURNING *` already gives the current row, so this is the same data, not an additional query; listed for clarity of what data the rest of the sequence operates on).
7. `SELECT ... FOR UPDATE` the Payment row by `payment_id`.
8. `SELECT ... FOR UPDATE` the `clinic_registrations` row by the Payment's own `clinic_registration_id` — **this is the stable existing parent row locked to serialize competing initial activations** (see [Transaction and Locking Strategy](#transaction-and-locking-strategy)).
9. Load (no lock needed — immutable once claimed) the CommercialOffer by `Payment.commercialOfferId`.
10. Validate: Payment status is `succeeded`; `tenant_id` matches across Payment/CommercialOffer/`clinic_registrations.reserved_tenant_id`; CommercialOffer identity matches what the application expects; amount/currency match the CommercialOffer's payable obligation.
11. `findByTenantId` on `subscriptions` (safe now — protected by the step-8 lock, and decided strictly by transaction-commit order, never by timestamp, per locked CTO Decision 3): if a Subscription already exists for this tenant and it was **not** created by this same `payment_id`, classify `superseded` and complete as `ignored` — this is the default, locked outcome for a later competing Payment observing an existing Subscription for the same tenant. The narrower `reconciliation_required` path applies only when the existing Subscription's own state additionally indicates this Payment is renewal/reactivation-shaped evidence, not a pure initial-activation race (see [ADR-011](./decisions/ADR-011-Initial-Subscription-Activation.md)'s own outcome policy) — and skip to step 16.
12. If eligibility fails any other check, classify accordingly (`invalid_evidence`/`tenant_mismatch`/`commercial_offer_mismatch`/`obligation_mismatch`) and skip to step 16.
13. Create `Subscription` in `Pending` via `Subscription::create(...)`, with `id` = the application's reserved `subscription_id`, and the Annual Date Algorithm's `starts_on`/`ends_on` (see next section).
14. `Subscription::activate($now)`.
15. `SubscriptionRepositoryInterface::save($subscription)` (a fresh insert).
16. Write the `system`-actor `AuditEntry` (one of the four approved actions, matching the outcome).
17. `complete($applicationId, $claimToken, $status, $resultCode, $now)`.
18. If the outcome is `reconciliation_required`, `SubscriptionActivationReconciliationCaseRepositoryInterface::open(...)` — inside the same transaction.
19. If (and only if) the outcome is `applied` with a genuinely new Subscription (not `already_reflected`), insert the `SubscriptionActivated` row into `subscription_integration_outbox` — inside the same transaction.
20. Transaction commits. All of steps 13–19 (whichever subset actually ran for this outcome) commit atomically or none do.

**D. Retry handling**: a caught transient-failure exception outside the transaction's own boundary triggers `complete(..., 'retry_pending', ..., $nextAttemptAt)` and `dispatch($applicationId, $delay)`, mirroring `ApplyAuthoritativePaymentVerificationService`'s own catch-block shape exactly.

**E. Terminal handling**: `quarantined`/`exhausted`/`ignored`/`reconciliation_required`/`applied` are all reached via `complete()` inside the transaction (steps 16–17), never via a separate out-of-transaction call — consistent with "no participating repository may independently commit."

**Outcomes producing no Subscription and no outbox event**: `already_reflected` (duplicate, nothing new to create), `superseded`/`ignored`, `reconciliation_required`, `invalid_evidence`/`quarantined`, `tenant_mismatch`/`quarantined`, `commercial_offer_mismatch`/`quarantined`, `obligation_mismatch`/`quarantined` — only the genuine first-time `applied` outcome produces both.

## Annual Date Algorithm

Explicit, dependency-free algorithm — no reliance on undocumented PHP overflow behavior, using only `DateTimeImmutable` and `DateInterval` in a way whose result is checked, not assumed:

```php
function calculateAnnualTerm(DateTimeImmutable $activationInstantUtc): array
{
    // starts_on: UTC calendar date only, no time component.
    $startsOn = $activationInstantUtc->setTimezone(new DateTimeZone('UTC'))->setTime(0, 0, 0);

    // next_anniversary = starts_on + 1 calendar year, explicit and checked.
    $nextAnniversary = $startsOn->add(new DateInterval('P1Y'));

    // ends_on = next_anniversary - 1 calendar day (inclusive term end).
    $endsOn = $nextAnniversary->sub(new DateInterval('P1D'));

    return [
        'starts_on' => $startsOn->format('Y-m-d'),
        'ends_on' => $endsOn->format('Y-m-d'),
    ];
}
```

`DateInterval('P1Y')` added to a `DateTimeImmutable` is PHP's own explicit, documented calendar-arithmetic operation (not a raw timestamp/seconds offset) — this is the "explicit algorithm," not an accidental reliance on overflow. The February 29 roll-forward behavior this produces (see test vectors) is PHP's own documented calendar-overflow rule for `DateInterval` arithmetic on a non-existent target date, and this algorithm's design **relies on and accepts** that documented behavior deliberately, rather than fighting it — the alternative (manually detecting Feb 29 and special-casing it) would risk *contradicting* ADR-011's own explicit instruction ("Use roll-forward behavior for February 29 ... Do not use a fixed 365-day calculation") if implemented incorrectly, whereas trusting the language's own calendar-interval arithmetic and asserting the result in tests is the safer, more explicit path.

**Test vectors** (to be implemented as unit tests when this plan is coded, not now):

| `starts_on` (activation UTC date) | `next_anniversary` | `ends_on` |
|---|---|---|
| 2026-07-25 (normal date) | 2027-07-25 | 2027-07-24 |
| 2028-02-29 (leap-year crossing) | 2029-03-01 | 2029-02-28 |
| 2027-02-28 (non-leap Feb 28) | 2028-02-28 | 2028-02-27 |
| 2024-02-29 (leap-year start, next target also has Feb 29) | 2025-03-01 (2025 is not a leap year) | 2025-02-28 |
| 2026-12-31 (year-end) | 2027-12-31 | 2027-12-30 |
| Activation at 2026-07-25T23:59:59.999999Z (near UTC midnight) | `starts_on` must still resolve to `2026-07-25`, not `2026-07-26` — the algorithm's `setTime(0,0,0)` step operates on the already-UTC-converted instant's own calendar date, so this is deterministic regardless of how close to midnight the transaction commits | 2027-07-24 |

The "near UTC midnight" vector is included specifically to prove the algorithm never depends on wall-clock rounding or a non-UTC default timezone silently shifting the calendar date by one day — the explicit `setTimezone(UTC)` call before `setTime(0,0,0)` is the guarantee.

## Reconciliation Design

`SubscriptionActivationReconciliationCase` — data model per [docs/35](./35_SUBSCRIPTION_ACTIVATION_ERD.md#subscription_activation_reconciliation_cases).

**Deterministic uniqueness identity**: `UNIQUE(subscription_activation_application_id)` — one case per application, never per Payment or per tenant directly (an application is already 1:1 with a source event, which is already 1:1 with a Payment, so this transitively prevents duplicate cases for the same underlying event without needing a second constraint).

**Repository contract**:

```php
interface SubscriptionActivationReconciliationCaseRepositoryInterface
{
    public function open(string $applicationId, string $paymentId, string $tenantId, string $reasonCode, DateTimeImmutable $openedAt): string;
}
```

Single method, matching `PaymentReconciliationCaseRepositoryInterface`'s own minimal shape — a distinct interface, never extending or reusing it, per ADR-011's explicit instruction.

**Transaction participation**: `open()` is called from inside the same activation transaction (step 18 above) — never as a separate, independently-committed call.

**Safe metadata policy**: only opaque identifiers and a stable `reason_code` token; no raw evidence, no provider data, no PII — identical posture to every other audit/reconciliation record built this session.

This increment **only opens cases** — no resolution, refund, or manual-recovery method exists on this interface, and none should be added by this plan.

## Subscription Outbox Design

**Comparison**:

- **A. Subscription-specific repository/job/service** (a `PostgresSubscriptionIntegrationOutboxRepository`, `PublishSubscriptionOutboxService`, `PublishSubscriptionOutboxJob`, structurally identical to but not sharing code with the Payment-side classes): matches ADR-011's own explicit instruction ("Create a new, Subscription-owned outbox... Do not reuse `payment_integration_outbox`") and this session's own established precedent of NOT sharing `PaymentApplicationTransactionInterface`/`PaymentApplicationRetryPolicy` across modules-within-a-module boundaries. Minimal duplication (one small service class, ~50 lines, already proven correct once this session) for a large, clear independence benefit.
- **B. A narrowly shared infrastructure abstraction** (e.g. a shared `AbstractOutboxPublisher` both Payment and Subscription outbox services extend, parameterized by table name): would reduce line-count duplication, but couples two modules' operational behavior to one shared class the moment either needs to diverge (e.g. if Subscription's outbox ever needs a different lease duration or a different failure-classification rule) — a real risk given this increment already needed to fix a real bug in the Payment-side publisher's failure handling earlier this session; a shared abstraction would have made that fix a two-module change instead of one.
- **C. A generic cross-module outbox framework**: explicitly the kind of premature generalization the task instructs against ("Do not create a premature generic framework merely to avoid duplication"), and there is still only ever exactly two consumers of this pattern in the whole codebase (Payment, and now Subscription) — not enough real variation to design a good abstraction from, and no approved document asks for one.

**Approved and locked: Option A (CTO Decision 7).** No generic cross-module outbox framework is created in this increment. Two proven, independent, ~50-line service classes are cheaper to reason about, cheaper to test in isolation, and safer to evolve independently than either shared alternative, and this is exactly the choice ADR-011 itself already made explicit.

**Exact design**: columns, event ID format, and payload per [docs/35](./35_SUBSCRIPTION_ACTIVATION_ERD.md#subscription_integration_outbox) and [docs/34](./34_SUBSCRIPTION_ACTIVATION_ARCHITECTURE.md#outbox-contract). Claim/lease/attempts/next-attempt/exhausted behavior: identical in shape to this session's own already-fixed `PublishPaymentOutboxService` (including the failure-handling catch block this session added — the Subscription-side sibling must include the equivalent catch block from its very first implementation, not retrofit it later as Payment's needed to be).

## Transaction and Locking Strategy

**`SubscriptionActivationTransactionInterface`** (new, Contracts): `run(callable $operation): mixed` — structurally identical to `PaymentApplicationTransactionInterface`, bound to its own `PostgresSubscriptionActivationTransaction` implementation (catching the same `QueryException`/stale-write-equivalent classes and rethrowing as a new `TransientSubscriptionActivationException`), never the same bound instance as Payment's.

**Which row is locked to serialize competing initial activations**: `clinic_registrations`, by the row corresponding to the Payment's `clinic_registration_id` — the only row that (a) already exists before any Subscription does, (b) is 1:1 with the `tenant_id` this increment cares about serializing on, and (c) is already participating in the same module's data model (no new cross-module dependency introduced).

**Lock ordering**: Payment row first (step 7), then `clinic_registrations` row (step 8) — a fixed, consistent order across every activation transaction, chosen specifically to avoid deadlock: since every activation transaction locks exactly these two rows in exactly this order, no two transactions can ever hold one and wait on the other in reverse order.

**Optimistic vs. pessimistic**: pessimistic (`SELECT ... FOR UPDATE`) for both locked rows, for the same reason `18_AGGREGATE_DESIGN.md`'s own Optimistic Locking Policy already carves out an exception for Booking's conflict-prevention transaction — "the cost of a failed [activation] attempt... may justify a stronger guarantee than optimistic retry alone," and a failed activation is exactly as costly here (a real customer's real payment, not a low-stakes retry). `subscriptions.version` itself remains optimistic-locking-shaped (for future update paths) but is not the concurrency mechanism for *this* increment's create-path race.

**Deadlock avoidance**: the fixed lock order above, plus the fact that no other transaction in the system ever locks these two specific tables in the reverse order (confirmed: no other Application service locks both `payments` and `clinic_registrations` together today).

**Transaction retry classification**: a caught lock-timeout or serialization-failure exception is transient (per [Activation Application Design](#activation-application-design)'s retry policy); a caught unique-constraint violation on `subscriptions.tenant_id` is **not** transient — it is the expected signal for the `superseded` outcome path (see [Subscription Persistence Design](#subscription-persistence-design)); a caught unique-constraint violation on `subscriptions.payment_id` is treated as transient only defensively (it should be structurally unreachable given the applications table's own `UNIQUE(payment_id)`, but the retry classification handles it gracefully rather than crashing if it ever occurs).

**Outside the transaction**: event registration (step A), the claim statement itself (step B) — both single, already-atomic statements that do not need to share a transaction with the rest of the sequence, matching ADR-010's own established precedent exactly.

**Inside the transaction**: every one of steps 6–19 above. No participating repository commits independently.

## Migration Order

**Locked CTO Decision 4 — the approved rollout, exactly**: add nullable columns → deploy dormant/new-write support → populate the column for all new records → run a preflight query → if no legacy `NULL` rows exist, tighten constraints → if legacy rows exist, **stop deployment** and require a separately approved, explicit data-migration mapping → only then add `NOT NULL` and uniqueness constraints. No migration may generate a random `TenantId` for an existing production row. `NOT NULL` tightening is its own deployment gate, never an automatic assumption. Disposable local/test databases may simply be reset instead of running this gate.

Proposed sequence (not created here):

1. **`..._add_reserved_tenant_id_to_clinic_registrations.php`** — add `reserved_tenant_id uuid NULLABLE`. No unique constraint yet. Dormant: no code path reads this column for a decision.
2. **`..._add_tenant_id_to_commercial_offers.php`** — add `tenant_id uuid NULLABLE`. Add the plain index. Dormant, same reason.
3. **`..._add_tenant_id_to_payments.php`** — add `tenant_id uuid NULLABLE`. Add the plain index. Dormant, same reason.
4. **Application-level rollout window (dormant, new-write-only support)**: new code begins populating `reserved_tenant_id`/`tenant_id` on every newly-`submit()`'d registration, newly-prepared CommercialOffer, and newly-created Payment going forward. Historical rows are not touched by this step; they remain `NULL` until the preflight query in step 5 decides what happens next.
5. **Preflight query (report-only, run before any tightening migration)**: query for remaining `NULL` `reserved_tenant_id`/`tenant_id` rows among still-relevant records. **If none exist**, proceed to step 6. **If any legacy `NULL` rows exist**, stop deployment here — do not tighten constraints — and obtain a separately approved, explicit data-migration mapping for those specific rows before continuing. This document does not assume which outcome the preflight query will find in production.
6. **`..._add_unique_reserved_tenant_id_to_clinic_registrations.php`** (run only once the step-5 gate has cleared) — add `NOT NULL` and `UNIQUE(reserved_tenant_id)`.
7. **`..._create_subscriptions_and_activation_tables.php`** — creates all four new tables from [docs/35](./35_SUBSCRIPTION_ACTIVATION_ERD.md) in one migration (mirroring how the prior increment's `2026_07_25_000001_create_payment_verification_application_tables.php` created three related tables together), including all `CHECK` constraints, `UNIQUE` constraints, indexes, and foreign keys from that document.

**Rollback order**: strict reverse — drop the four new tables (step 7) first, then reverse step 6 (drop `NOT NULL`/the unique index), then reverse steps 1–3 (drop the three new columns) in reverse creation order.

**Historical data policy — resolved, not open.** No migration manufactures a `TenantId` for any real historical row. The step-5 preflight query is the single deployment gate: it either confirms no legacy `NULL` rows remain (tightening proceeds) or it stops deployment and requires a separately approved, explicit data-migration mapping (tightening does not proceed until that mapping is approved). This document does not need to know in advance which branch production data will take — the gate itself is the approved decision.

## Implementation Increment Plan

The task's suggested 5-increment split is challenged on one point: **Increment 2 as described ("Subscription persistence and annual period policy") would leave a transactionally incomplete intermediate state** if implemented and merged before Increment 3 exists — a `SubscriptionRepositoryInterface`/`save()` path with no caller is harmless (dead code, not wired), but if Increment 2 is interpreted as also wiring the annual-period policy into any live code path before the full activation transaction (Increment 3) exists, that would create exactly the "partially enabled" state the task explicitly forbids. **Recommendation: keep the 5-increment shape, but make explicit that Increments 1–4 are unwired/dormant until Increment 5's own final wiring step**, so no increment before the last one is reachable from any real event.

1. **TenantId propagation and persistence foundation, plus the Payment-side `event_version` precondition** — `ClinicRegistration`/`CommercialOffer`/`Payment` aggregate changes, new columns (nullable), mapper changes, unit + PostgreSQL round-trip tests; and, per locked CTO Decision 6, the additive `event_version` column/field on `payment_integration_outbox`/`PaymentIntegrationOutboxEvent` (starting at `1`) — a Payment-side integration-contract hardening change with no Payment Domain behavior change. No new Subscription table yet. No behavior change to any existing consumer of these aggregates beyond the new fields existing and being populated. **Dormant**: nothing yet reads the new columns for a decision, and no Subscription-side consumer exists yet to read `event_version`.
2. **Subscription persistence and annual period policy** — `SubscriptionRepositoryInterface` + Postgres implementation + `subscriptions` table migration; the pure `AnnualTermCalculator` unit-tested in isolation with all six test vectors. **Dormant**: no Application service calls `save()` yet; the calculator is a pure function with no caller.
3. **Activation application, transaction and reconciliation** — `SubscriptionActivationApplication*` contracts/infrastructure, `subscription_activation_applications`/`subscription_activation_reconciliation_cases` tables, `ActivateSubscriptionFromVerifiedPaymentService`'s full transaction sequence, `SubscriptionActivationAuditTrail`. **Still dormant**: the service exists and is fully testable in isolation (exactly as `ApplyAuthoritativePaymentVerificationService` was built and tested before its own queue listener existed), but nothing dispatches it yet.
4. **Subscription outbox delivery** — `subscription_integration_outbox` table, `PublishSubscriptionOutboxService`/job, scheduler registration. **Still dormant**: nothing writes to this table yet, since Increment 3's service doesn't call it until wired.
5. **Wiring, PostgreSQL concurrency/rollback proof, and architecture tests** — the queue listener on `VerifiedPaymentSucceeded` (the only step that makes the whole vertical slice *live*), every atomic-rollback test, every concurrency fork test, every architecture-boundary test. **This is the single increment where the feature becomes reachable from a real event** — consistent with "No increment may leave production behavior partially enabled" and "Feature wiring should remain disabled until the complete vertical slice is ready."
