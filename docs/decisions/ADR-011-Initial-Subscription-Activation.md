# ADR-011: Initial Subscription Activation

## Status

Accepted.

## Date

2026-07-22

## Decision Owner

Chief Technology Officer

## Context

ADR-007 names Subscription as the step immediately after Payment in the provisioning order but does not define the mechanism. ADR-010 delivers a durable, authoritative Payment outcome (`VerifiedPaymentSucceeded`, written to a transactional outbox) but explicitly excludes Subscription activation from its own scope. No Subscription repository, persistence, or application service exists yet; the `Subscription` aggregate itself (lifecycle, entitlement, value objects) is already accepted and unmodified by this ADR.

This increment defines only the first activation of a Subscription: `no Subscription → Pending → Active`, triggered by one authoritative successful Payment. Renewal, reactivation, expired-to-active, cancelled-to-active, plan change, onboarding, Tenant provisioning, notifications, refunds, and reconciliation resolution are explicitly out of scope and remain governed by their own future decisions.

## Decision

**Tenant identity is reserved, not provisioned, before checkout.** `TenantId` is an immutable opaque UUID established when Clinic Registration is submitted for the commercial onboarding flow — the existing `Draft → Submitted` transition — and carried unchanged through `CommercialOffer`, `Payment`, and `Subscription`. No `Approved`/`UnderReview` status is introduced to support this; the existing `submit()` transition is the reservation point. Generation belongs to the Application layer, never to the aggregate: an Application-layer generator produces the identifier exactly once, and `SubmitClinicRegistrationService` passes it into `clinicRegistration.submit(tenantId, occurredAt)` as a parameter. The `ClinicRegistration` aggregate itself never depends on an identifier-generator interface, never generates the identifier, rejects any attempt to replace an already-reserved `TenantId`, and preserves the value unchanged through reconstitution and for the rest of its lifetime. Reservation is not Tenant provisioning or activation — `Tenant::provision()` still runs later, using the same reserved identifier, after Subscription activation, unchanged from ADR-007's provisioning order. This resolves the timing gap ADR-002/ADR-007 left open without changing that order.

**`TenantId` crosses module boundaries only as an opaque UUID string.** No Shared Kernel is introduced solely for `TenantId`, and no bounded context imports another context's Domain `TenantId` value object directly. Each bounded context may construct its own independently validated local value object from the same opaque string. Queue jobs carry only this opaque identifier, never a typed cross-module reference.

**Subscription does not exist before a successful Payment.** There is no pending, unpersisted Subscription waiting for payment. Activation is the same transaction that creates the Subscription in `Pending` and immediately calls its existing, unmodified `activate()` method to reach `Active`.

**Orchestration is a durable `SubscriptionActivationApplication`**, one-to-one with the triggering `VerifiedPaymentSucceeded` outbox event, following the exact pattern ADR-010 established for `PaymentVerificationApplication`: an opaque claim token, a two-minute lease, and a five-attempt local retry policy configured independently of Payment's own policy. The integration-event consumer's only job is to register the application and schedule processing; it never mutates Subscription directly, and Payment's own Domain and Application layers never call a Subscription repository.

**Identity is database-enforced**, not merely composite. `subscription_activation_applications` carries three independent unique constraints: `UNIQUE(source_event_id)`, `UNIQUE(payment_id)`, and `UNIQUE(subscription_id)`. `subscription_id` is generated once, at registration, and every retry of the same application reuses it — the identifier is never regenerated by a later attempt.

**`subscriptions` itself is also database-enforced, not only the application table.** `subscriptions` carries `UNIQUE(tenant_id)` and `UNIQUE(payment_id)`: one Tenant owns exactly one Subscription lifecycle aggregate, and one Payment creates at most one initial Subscription; a future renewal transition updates that same aggregate rather than creating another. `subscriptions.payment_id` is immutable initial-activation lineage and is never overwritten by a later renewal Payment. `UNIQUE(commercial_offer_id)` is deliberately not added — it protects no invariant `UNIQUE(payment_id)` does not already give, since one Payment claims at most one CommercialOffer.

**Concurrent competing activations for the same Tenant are serialized by a fixed lock order and transaction-commit order, never by timestamp comparison.** The activation transaction locks, in this order: (1) the Payment row, (2) the stable, already-existing `clinic_registrations` row for that Tenant, then (3) queries `subscriptions` by `tenant_id`. The first transaction to commit wins. A later competing Payment that, after acquiring its own lock, observes a Subscription already committed for the same Tenant completes with status `ignored` and result code `superseded` — never by comparing creation timestamps, never using CommercialOffer as the concurrency parent, and never introducing a new purchase identity.

**The annual term uses calendar-anniversary arithmetic, never a fixed 365-day offset.** `starts_on` is the UTC calendar date of the activation transaction. The next anniversary is `starts_on` plus one calendar year; `ends_on` (inclusive) is that anniversary minus one calendar day. A 2028-02-29 start rolls forward to a 2029-03-01 anniversary, giving `ends_on = 2029-02-28` — leap-year roll-forward, not clamping.

**One PostgreSQL transaction contains, atomically:** loading Payment, loading the immutable CommercialOffer, revalidating eligibility, creating and activating Subscription, saving it, writing a system-actor financial `AuditEntry`, completing the activation application, opening a reconciliation case where applicable, and inserting a `SubscriptionActivated` row into a new, Subscription-owned `subscription_integration_outbox`. No participating repository commits independently.

**Reconciliation is a Subscription-specific concept.** `SubscriptionActivationReconciliationCase` is its own table and repository; it does not reuse or extend `PaymentReconciliationCaseRepositoryInterface`. This increment only opens cases — it does not resolve, refund, or manually recover them, matching ADR-010's own precedent.

**The Subscription-owned outbox is Option A**: a Subscription-specific repository, publisher service, queue job, retry policy, and scheduler sweep. This increment does not create a generic cross-module outbox framework.

**Before this activation consumer is wired, Payment's own integration-event contract requires one additive hardening change.** `payment_integration_outbox`/`PaymentIntegrationOutboxEvent` gains `event_version`, starting at `1`. This is additive integration-contract hardening only — it changes no Payment Domain state behavior. The consumer's policy for the source event is: an unsupported event type is ignored without registering an application; a supported type at `event_version = 1` is registered; a recognized type at an unsupported version is quarantined; malformed normalized identifiers are quarantined; a duplicate `source_event_id` returns or reuses the existing activation application.

**Outcomes are classified, never guessed.** Valid first activation is `applied`. A duplicate source event or a Payment already activated is `already_reflected`. A Payment that is not succeeded, a tenant mismatch, a CommercialOffer mismatch, or an amount/currency mismatch is a distinct `invalid_evidence` / `tenant_mismatch` / `commercial_offer_mismatch` / `obligation_mismatch` result and moves the application to `quarantined`. An old Payment superseded by a newer valid activation is `superseded` and `ignored`. A successful Payment that would imply renewal, reactivation, or targets an already-existing Subscription is `reconciliation_required` — this increment never renews, reactivates, refunds, or resolves automatically.

**Audit uses the `system` actor** and four approved actions only: `subscription.activation.applied`, `subscription.activation.ignored`, `subscription.activation.reconciliation_opened`, `subscription.activation.quarantined`. Only opaque identifiers and result codes are recorded — never raw payloads, provider data, or PII.

The full technical design — activation-application lifecycle and claim/lease mechanics, the eligibility matrix, the outbox event contract, table/column/constraint definitions, and the test strategy — is recorded in [docs/34_SUBSCRIPTION_ACTIVATION_ARCHITECTURE.md](../34_SUBSCRIPTION_ACTIVATION_ARCHITECTURE.md).

## Consequences

A Subscription can now come into existence and reach `Active` from exactly one authoritative Payment outcome, with duplicate delivery, crash recovery, and concurrent workers handled the same way ADR-010 already proved for Payment verification. Tenant Provisioning gains a reserved, stable `TenantId` to provision against without moving earlier in the provisioning order. Renewal, reactivation, plan change, onboarding, and Tenant provisioning remain future work; this ADR does not implement or approve any of them. `Subscription::reactivate()` is unmodified, and no `reactivateWithNewTerm()`-style method is introduced by this increment.

**No migration may generate a random `TenantId` for an existing production row.** The approved rollout is: add `tenant_id` as nullable → deploy dormant, new-write-only support → populate `tenant_id` for all newly-submitted or newly-created records → run a preflight query for remaining legacy `NULL` rows → tighten to `NOT NULL` and add uniqueness only if none remain; otherwise stop deployment and obtain a separately approved, explicit data-migration mapping before tightening. `NOT NULL` tightening is its own deployment gate, never an automatic assumption. Disposable local/test databases may simply be reset.

## Relationship to earlier decisions

ADR-007's provisioning order (`Clinic Registration → Commercial → Payment → Subscription → Tenant Provisioning → Internal Onboarding`) is unchanged and is not superseded — see the accompanying narrow addendum to ADR-007 clarifying only that `TenantId` reservation happens when Clinic Registration is submitted for the commercial onboarding flow, while Tenant aggregate provisioning still happens after Subscription activation. ADR-010 is unchanged; this ADR is the deferred "future work" its own Consequences section named for Subscription activation. ADR-006, ADR-008, and ADR-009 are unaffected.
